# Защита от спама, ботов и атак

## Что уже есть в каркасе
- Ограничение размера HTTP-запроса по Content-Length.
- Общий rate limit по IP и отдельный лимит на dev-эндпоинтах по идентификатору.
- Заголовки защиты и отключение интерактивной документации FastAPI в production.
- Поддержка Cloudflare Turnstile Siteverify через `POST /human/verify`.
- Короткоживущие подписанные HMAC tickets, одноразовые коды, привязка к каналу/пользователю и защита от повторного использования ticket nonce.
- Секреты для CAPTCHA и подписи берутся из окружения, не из Git.

## Важное ограничение текущей версии
Human gate **ещё не включён в реальный входящий поток Telegram/Instagram/WhatsApp**: платформенные webhook-обработчики пока являются заготовками. Перед production каждый адаптер обязан:
1. Проверить подлинность webhook по правилам соответствующей платформы.
2. Получить идентификатор пользователя из проверенного события.
3. Создать короткоживущий ticket через `create_ticket(channel, external_user_id, TICKET_SIGNING_SECRET)`.
4. Отправить ссылку на HTTPS-страницу проверки с ticket и подписью.
5. Принять одноразовый код только от того же пользователя и вызвать `consume_human_code(f"{channel}:{external_user_id}", code)`.
6. До успешной проверки не запускать ИИ, не выдавать вопросы и не выполнять дорогостоящие операции.
7. После проверки проверять `is_human_verified(f"{channel}:{external_user_id}")` для последующих событий.

**Не создавайте ticket на основании channel/user_id, пришедших от браузера.** Ticket выдаётся только после верификации подписи платформенного webhook. Секреты должны быть случайными и храниться в secret manager. Turnstile требует зарегистрировать сайт и настроить разрешённые домены; публичная страница CAPTCHA и ключ сайта в этом репозитории пока не созданы.

## Что CAPTCHA может и чего не может
Ни одна CAPTCHA не доказывает с абсолютной уверенностью, что пользователь — человек: возможны сервисы решения CAPTCHA, браузерная автоматизация и фермы аккаунтов. Цель — повысить стоимость массового злоупотребления, не заявить математически невозможную гарантию.

## Обязательная защита production
- Reverse proxy/WAF/CDN с защитой от DDoS и лимитами до приложения.
- Проверка подписи вебхуков Meta; проверка Telegram secret token для webhook; защита от повторной доставки и дедупликация event ID.
- HTTPS; доверять forwarded headers только от настроенного proxy.
- Redis или другое общее хранилище rate limit для нескольких инстансов; SQLite limiter предназначен для MVP и не является распределённой защитой.
- Аутентификация и авторизация всех административных маршрутов; dev-маршруты не публиковать.
- Таймауты, ограничения параллелизма и расходов на LLM, квоты на пользователя, circuit breaker.
- Валидация входов, безопасная обработка URL/вложений, запрет выполнения команд/кода из сообщений, отсутствие секретов в логах.
- Регулярные обновления зависимостей, secret scanning, резервное копирование, мониторинг ошибок и план реагирования на инциденты.
- Перед запуском: тесты rate limit, replay, webhook signature, payload limits, prompt injection и проверки отказа.

## Конфигурация
В `.env` задаются `TURNSTILE_SECRET_KEY` и `TICKET_SIGNING_SECRET`. Никогда не коммитьте реальные значения. Публичный ключ Turnstile относится к frontend и настраивается отдельно; секретный ключ используется только на сервере.
