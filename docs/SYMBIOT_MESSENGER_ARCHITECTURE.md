# YUGATNEO Symbiot + Messenger: архитектура MVP

Статус: технический проект, не развёрнутый сервис.

## Разделение ответственности

**Symbiot** — коучинговые диалоги, рефлексия, пользовательское колесо баланса (до 12 настраиваемых лучей), история оценок, цели, планирование и согласованные рекомендации. Не выдаёт клинических диагнозов, не ведёт скрытое наблюдение и не принимает решения за пользователя.

**Messenger** — личные и групповые чаты, голосовые заметки, обмен файлами, уведомления, явно инициированное подключение ИИ к разговору. Telegram остаётся первым внешним каналом, но не единственным интерфейсом.

**Connector** — авторизованный API и MCP-интерфейс для ChatGPT и других клиентов. Он не является автоматически установленным плагином.

## Продуктовые требования

1. Колесо создаётся пустым: пользователь выбирает 1–12 сфер через каталог или задаёт собственное название. Каталог помогает рефлексии, не навязывает универсальную норму.
2. Снимок состояния содержит оценки 0–10, дату, необязательную заметку и версию схемы сфер. Старые снимки не перезаписываются.
3. Цель содержит текущую оценку, желаемую оценку, целевую дату, первый шаг и историю выполненных действий. Связь с исходным снимком сохраняется.
4. Экспорт календаря в ICS работает без доступа к личному календарю; двусторонняя синхронизация требует OAuth и отдельного согласия.
5. Голосовая заметка записывается только по явному действию пользователя. Хранение и транскрипция — раздельные согласия.
6. ИИ участвует в групповой беседе только после явного приглашения и с видимым индикатором. Для анализа аудио/видео требуется отдельное согласие всех затронутых участников.
7. Messenger не должен скрытно копировать чужие переписки или записывать звонки. Удаление, экспорт и сроки хранения данных проектируются до публичного запуска.
8. Доступ к приватным данным — по пользовательской идентичности и разрешениям, а не по переданному клиентом идентификатору.
9. Платёжные и коучинговые функции изолированы: базовые вопросы доступны бесплатно; оплата не влияет на оценку пользователя.

## Архитектура

- `app/services/`: ядро коучинга, диагностика, безопасность, каталог вопросов.
- `app/channels/`: Telegram и будущие транспортные адаптеры.
- `app/api/`: версионированный REST API с авторизацией.
- `integrations/mcp/`: удалённый MCP-сервер с минимальными разрешениями.
- `clients/messenger/`: будущий веб/PWA-клиент с доступностью на телефонах и ПК.
- `storage/`: серверная БД с миграциями, резервным копированием и политикой удаления.

## Контракты данных

`WheelSphere`: id, owner_id, label, catalog_key?, created_at.

`WheelSnapshot`: id, owner_id, recorded_at, sphere_scores[], note?, schema_version.

`Goal`: id, owner_id, sphere_id?, baseline_snapshot_id?, baseline_score?, target_score?, target_date?, first_step?, status.

`GoalEvent`: id, goal_id, occurred_at, event_type, note?, source.

`Conversation`: id, kind (direct/group), participants, ai_enabled, retention_policy.

`Message`: id, conversation_id, author_id, type, created_at, content_reference, consent_metadata?.

Не хранить пароли или токены в исходном коде. Схемы являются целевыми, а не утверждением о существующей реализации.

## План внедрения

**Этап 1:** API и модель данных для версионированных снимков колеса, целей и событий. Тесты изоляции пользователей.

**Этап 2:** Telegram-бот с меню сфер, сохранением снимков и ICS-экспортом.

**Этап 3:** веб/PWA Messenger: вход, переписка, уведомления, история коучинга.

**Этап 4:** удалённый MCP с OAuth, проверкой прав, журналом действий и подтверждением операций записи.

**Этап 5:** голосовые заметки, согласованная транскрипция, доступный дизайн и пилотное тестирование.

## Критерии приёмки MVP

- Пользователь создаёт собственные сферы и сохраняет два снимка без потери истории.
- Создаёт цель, первый шаг и скачивает корректный ICS.
- Вторая учётная запись не может прочитать или изменить чужие записи.
- Ошибки авторизации и некорректные оценки обрабатываются без раскрытия данных.
- Пользователь может экспортировать и удалить данные.
- Сборка и тесты проходят в CI.

## Границы достоверности

Прогресс проекта оценивается по проверенным тестам и работающим функциям, а не по количеству документов. Данный файл фиксирует техническое задание; перечисленные функции не следует считать реализованными до появления кода и успешных проверок.
